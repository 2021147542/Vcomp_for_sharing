# Cassandra F2Load iteration graphs

This bundle renders one independent baseline-versus-F2Load graph for each
completed implementation iteration following the ordered multi-partition
design request. Each graph contains the measurements available for that exact
version only; workload results from another VComp database are not carried
forward into later files.

## Measurement boundaries and caveats

- Baseline completion time spans native CQL loading, the final flush, and UCS
  compaction drain. F2Load time is the `VCOMP_RESULT` descriptor simulation,
  materialization and import interval; post-import automatic-compaction I/O is
  separately recorded by the runner and is not included in this plotted time.
- Device writes are `md0` disk-counter deltas over those runner-defined load
  intervals. Write amplification is device writes divided by final physical
  bytes using the same convention as the preceding Cassandra comparison
  figures.
- Visible-row deltas and final physical-size deltas are printed independently:
  matching size does not imply an exact logical-key match. Every completed
  pair has a different baseline/F2Load fingerprint.
- The 100 GiB unbiased-v3 A–F campaign was interrupted after A. Its independently
  completed MixGraph pair is included; B–F are correctly left absent.
- Both files labelled `seeded common scheduler` requested
  `cassandra.ucs.picker_seed=20260909`, but the baseline daemon used the
  00:48 Cassandra jar whose `Controller.random()` still returned
  `ThreadLocalRandom.current()`. Those files therefore must not be cited as
  proof of identical seeded tie-breaking. F2Load did use the newer classes.
