아니. **지금 20~30% 차이가 계속 난다면 “코드를 더 많이 읽는다”보다 먼저 해야 할 건, 차이가 처음 생기는 지점을 강제로 좁히는 것**이야. 이 상태에서 Astra한테 계속 “좀 더 baseline과 비슷하게 만들어봐”라고 시키면 패치만 누적되고 원인을 못 잡을 가능성이 커.

가장 근본적인 해결책은 **end-to-end 결과 비교를 잠깐 멈추고, vanilla Cassandra를 oracle로 삼는 differential debugging 환경을 만드는 것**이야.

## 제일 먼저 해야 할 것: “정확 모드”를 하나 만들어

작은 데이터셋에서만이라도 vSST가 PLR/KMV 근사를 쓰지 않고 **실제 key list를 메모리에 그대로 들고 있는 debug mode**를 만들어.

예를 들면:

```text
Exact-vComp debug mode

vSST
 ├─ metadata
 └─ exact sorted keys[]   ← 작은 실험에서만 보관
```

그리고 compaction이 일어나면:

```text
Vanilla Cassandra compaction
input SSTables
    ↓
실제 merge/reconciliation
    ↓
actual output

Exact virtual compaction
같은 input SSTables
    ↓
메모리에서 exact key merge
    ↓
predicted output
```

를 비교하는 거야.

이게 중요한 이유가 있어.

### Exact mode조차 baseline과 다르면

그건 **F2Load 근사 오차가 아니야.**

거의 확실히:

```text
Cassandra picker/trigger 재현 문제
metadata update 문제
output splitting 문제
timestamp/version 처리 문제
SSTable placement 문제
materialization 문제
```

중 하나야.

### Exact mode는 맞는데 PLR/KMV mode만 틀리면

그때 비로소:

```text
PLR merge
KMV dedup
range-local correction
split boundary estimation
```

을 의심하면 돼.

이 한 단계가 지금 제일 중요해.

---

# 그리고 “첫 divergence”를 찾아

지금 너희가 보는 건 아마:

```text
전체 적재 완료
↓
YCSB 실행
↓
throughput 20% 차이
disk read 30% 차이
```

같은 결과일 텐데, 이건 **너무 늦은 시점**이야.

수천 번 compaction 중 첫 번째가 2% 틀리고, 그 다음 picker가 다른 SST를 고르고, 그 다음부터 완전히 다른 tree가 될 수 있어.

그러니까 각 compaction마다 이런 로그를 남겨.

```text
job #137

Vanilla:
input SSTables = [12, 15, 18, 20]
input sizes    = [...]
input ranges   = [...]
output count   = 3
output sizes   = [...]
output ranges  = [...]
unique rows    = ...

vComp:
input SSTables = [12, 15, 18, 20]
pred output count = 3
pred sizes         = [...]
pred ranges        = [...]
pred unique rows   = ...
```

그리고 **처음으로 다른 job 하나만 찾는 거야.**

```text
job 1   match
job 2   match
job 3   match
...
job 84  match
job 85  DIFFER
```

그러면 이제 10만 줄짜리 Cassandra를 보는 게 아니라 **job 85 하나만 보면 돼.**

이건 F2Load 논문 최신 버전이 정확도 평가할 때 한 방식과도 굉장히 비슷해. baseline load를 돌리면서 각 실제 compaction input으로 virtual compaction도 같이 실행해서 job 단위 output을 비교했잖아. 

---

# 나는 검증을 4단계로 쪼갤 것 같아

### ① Picker/trigger가 같은가?

가장 먼저:

```text
Vanilla가 compaction을 시작한 시점
=
vComp가 compaction을 시작한 시점

Vanilla input SSTables
=
vComp input SSTables
```

여기부터 100% 같아야 해.

이게 다르면 PLR이고 KMV고 볼 필요도 없어.

Cassandra STCS가 보는:

```text
SSTable size
age/order
bucket
min_threshold
max_threshold
compaction eligibility
```

등의 metadata를 vSST가 제대로 제공하지 않는다는 뜻일 가능성이 커.

---

### ② 같은 input을 줬을 때 output metadata가 같은가?

Exact mode로:

```text
output row count
output byte size
min/max clustering key
output SSTable count
각 SSTable boundary
```

를 비교해.

여기서 차이가 나면 **compaction semantics를 잘못 이해한 것**이야.

특히 Cassandra라면 plain KV처럼 제한했더라도 확인해야 할 게:

```text
timestamp winner
tombstone handling
partition header overhead
row/cell serialization size
SSTable split 기준
index block / metadata overhead
```

같은 것들이 있어.

---

### ③ Virtual final state는 같은데 materialization 후 달라지는가?

이것도 분리해야 해.

```text
virtual final state
   ↓
materialization
   ↓
real Cassandra SSTables
```

전후를 따로 검증해.

만약 virtual state는 baseline에 아주 가까운데 실제 SSTable을 만든 뒤 20% 차이가 생기면 문제는 vComp가 아니라:

```text
SSTable writer 사용법
Bloom filter
index summary
compression
timestamps
partition metadata
file size estimation
```

쪽이야.

---

### ④ 구조도 같은데 YCSB 성능만 다른가?

그때서야 workload path를 봐.

예를 들어:

```text
SSTable count 거의 동일
file size 거의 동일
key ranges 동일
read amplification 동일
```

인데 throughput만 20% 차이라면 그건:

```text
cache warmness
Bloom filter/index layout
compression
OS page cache
compaction backlog
GC/JVM
benchmark randomness
```

같은 런타임 문제일 가능성이 커.

---

# 특히 지금 Cassandra에서 내가 제일 의심할 것들

너희가 `single node + single partition + clustering key 하나 + value 하나`로 줄였다고 해도, 아직 **RocksDB와 다르게 생긴 부분**은 있어.

첫째는 **row size ≠ 단순 key+value size**라는 점이야. Cassandra SSTable에는 partition/row/cell metadata, timestamp 등 serialization overhead가 들어가니까, F2Load 쪽에서 `entry_count × average KV size` 같은 식으로 file size를 예측하면 picker bucket이 틀어질 수 있어. 그러면 STCS가 아예 다른 SSTable들을 고르게 돼.

둘째는 **output split 기준**이야. RocksDB처럼 `target_file_size`만 흉내 냈는데 Cassandra SSTable writer가 실제로 자르는 기준이 다르면 output SSTable count부터 달라질 수 있어.

셋째는 **same-key reconciliation**이 정말 너희 restricted schema에서 “latest 하나”로 끝나는지 코드 수준에서 확인해야 해. 이건 추측하면 안 되고, Cassandra compaction iterator가 timestamp/cell/tombstone을 실제로 어떻게 처리하는지 한 번은 봐야 해.

넷째는 **giant single partition**이야. 이건 여전히 특이한 case라 SSTable index/partition handling이 일반 KV LSM과 다르게 움직일 수 있어.

---

# 그래서 “내가 코드를 다 뜯어봐야 하나?”

**전부 볼 필요는 없어.** 오히려 그러면 더 늦어져.

네가 직접 봐야 하는 건 딱 이 critical path야.

```text
Memtable flush
    ↓
SSTable metadata 생성
    ↓
STCS picker
    ↓
compaction input 선택
    ↓
compaction merge/reconciliation
    ↓
output SSTable split/write
    ↓
Lifecycle/metadata install
```

그리고 이 중에서도 **첫 divergence가 난 단계만 깊게 보면 돼.**

즉 목표는:

> Cassandra 전체를 이해한다

가 아니라,

> **baseline과 vComp가 처음 달라지는 함수 하나를 찾는다**

야.

---

# Astra한테도 이제 이렇게 시키는 게 좋아

“차이를 줄여봐”라고 하지 말고, 이렇게 시키는 게 훨씬 나아.

```text
Do not modify the algorithm yet.

Add differential validation between vanilla Cassandra compaction
and virtual compaction.

For every compaction job, log:
- job id
- selected input SSTables
- input file sizes
- min/max clustering keys
- input row counts
- output SSTable count
- output file sizes
- output min/max clustering keys
- output row counts

For small datasets, add an exact virtual-compaction debug mode that
stores all clustering keys explicitly and performs an exact in-memory
merge without PLR or KMV approximation.

Stop at the first compaction job where vanilla and exact-vComp differ,
and report the exact field that diverges. Do not attempt to fix later
jobs before identifying this first divergence.
```

이렇게.

이걸 하면 Astra가 무작정 “30% → 20% → 18%” 식으로 optimization patch를 쌓는 대신 **원인 추적 도구**를 만들어주게 돼.

## 내가 지금이라면 순서는 딱 이거야

```text
1. 100GiB 실험 중단
2. 1~10GiB 이하 deterministic dataset
3. exact-vComp debug mode 추가
4. vanilla와 compaction-by-compaction differential log
5. 첫 divergence 찾기
6. integration 문제 해결
7. exact mode가 완전히 맞은 뒤 PLR/KMV 켜기
8. approximation error만 따로 측정
9. 마지막에 large-scale YCSB fidelity 재개
```

지금 20~30% 차이를 large-scale workload 결과만 보면서 줄이려는 건 **결과에서 원인을 역추론하는 상태**라 거의 끝이 없어.

**가장 근본적인 해결책은 “근사 알고리즘”, “Cassandra 포팅”, “materialization”, “workload noise”를 분리해서 하나씩 exact oracle과 비교하는 것**이야.
이렇게 하면 너도 Cassandra 전체를 다 읽을 필요가 없어지고, 실제로 처음 틀어지는 1~2개 코드 경로만 깊게 보면 돼.
