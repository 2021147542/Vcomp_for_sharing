Fast-Forwarding LSM Tree Dataset Loading for
Fast and Realistic Benchmarking

Abstract

Benchmarking key-value (KV) stores is an essential step in
storage system development, performed repeatedly to evalu-
ate performance and reliability. Each evaluation should first
construct a test dataset, which developers typically build by
sequentially inserting a synthetic KV sequence. While this
natural accumulation produces a realistic testbed, it becomes
a severe bottleneck at scale. On log-structured merge-tree
(LSM-Tree) based KV stores, compaction repeatedly rewrites
the same data, and the resulting write amplification makes
loading a multi-terabyte dataset prohibitively slow.

We introduce F2Load, which fast-forwards natural accu-
mulation while removing its main cost: accessing the actual
key-value data. Our key insight is that the cumulative out-
come of compaction can be predicted from only a compact
summary of each Sorted String Table (SST). F2Load replaces
each SST with an in-memory virtual SST (vSST) and runs
virtual compaction along the original compaction path, mate-
rializing real SSTs only once the final LSM-Tree state is fixed.
This simulate-in-memory, write-once loading reduces loading
time by up to 47.9× over natural accumulation, while repro-
ducing its LSM-Tree access behavior and performance on
YCSB and MixGraph. In particular, it builds an 8 TB dataset
with 91 B KV size in under two hours, a load the baseline
would need a projected 47 hours to finish.

Introduction

Performance evaluation in storage system development is
not a one-time task. To validate a new design, configuration,
hardware, or workload, developers build an evaluation en-
vironment, run a workload, analyze the results, and repeat
with different parameters [12,26]. For the results to reflect a
real system, the environment must reproduce the scale and
workload characteristics of production as closely as possi-
ble. However, using production data directly is hard. Not
only are production traces costly to collect and a privacy
risk, but they also fix the scale, key distribution, and request

mix, so they cannot cover varied experimental conditions. Per-
formance evaluation in systems research therefore relies on
synthetic workloads and synthetic datasets, such as YCSB [9],
LinkBench [2], TAOBench [8], and MixGraph [6].
Among synthetic storage workloads, we focus on dataset
loading for log-structured merge-tree (LSM-Tree) based key-
value (KV) stores. These stores are actively studied, en-
hanced [18, 20, 35, 38], and widely deployed in produc-
tion [11, 21, 34]. Various storage applications also adopt
them as a storage backend [] and various performance evalua-
tions of storage components, such as databases, file systems,
and storage devices, also uses them as benchmarking work-
loads [4, 13, 17, 25].JK: 이런 말을 하고싶었던건가? Since
every such evaluation requires a dataset to run against, dataset
loading exists as a first step in the evaluation process.
To load a dataset, developers usually run a synthetic write-
only workload against the store. The LSM-tree inserts incom-
ing KV pairs into an in-memory buffer called a memtable.
When the memtable fills, the LSM-tree flushes its contents to
disk as a Sorted String Table (SST). Compaction then merges
and rewrites the resulting SSTs, progressively building the
dataset across the LSM-tree’s levels.
The problem is that this incremental construction—loading
the dataset progressively through compaction—becomes ex-
pensive at large scale. Modern services generate increasing
amounts of data [28]. Facebook reports hundreds of petabytes
across more than 30 applications [11]. Realistic evaluation
therefore needs synthetic datasets at the terabyte scale as
well. At that scale, however, incremental construction can
take tens of hours and can become a bottleneck in the eval-
uation process. At the 91 B KV size that Facebook reports
for its production workload [6], loading an 8 TB dataset takes
46.2 hours.
The cause is the write amplification of incremental con-
struction, which rewrites the same data many times through
compaction. As new data is loaded, compaction merges it
with overlapping SSTs already stored in the LSM-tree. In the
8 TB experiment, compaction wrote over 160 TB of SST data.
Each rewrite also consumed CPU time to merge keys and

rebuild SST filters and indexes. The loading process therefore
wrote tens of times the final dataset’s size, while repeatedly
paying the CPU cost of SST construction.
In the specific context of dataset loading, a subsequent
workload accesses only the SSTs in the final LSM-tree state.
In the 8 TB load, only 3.59% of all SSTs written during load-
ing remain in the final LSM-tree state. The rest are intermedi-
ate SSTs that are replaced during loading. Therefore, a loader
that directly builds the final LSM-tree state without material-
izing intermediate SSTs could reduce the I/O and CPU costs
of dataset loading.
Skipping the materialization of intermediate SSTs is
promising, but the loader must reproduce the final LSM-tree
state that incremental construction produces. This state in-
cludes the DB size, the number of populated levels, and the
placement and overlap of SSTs. It determines which SSTs a
lookup accesses and how much data subsequent compactions
rewrite, thereby shaping subsequent workload behavior. If the
loader does not accurately reproduce this state, the resulting
dataset can yield misleading evaluation results, regardless of
loading speed.
The final LSM-tree state also changes with the loading
configuration. Changes in dataset size, key uniqueness, and
SST options affect the resulting DB size and SST placement
across levels. A loader that builds the final LSM-tree state
directly must therefore meet two goals.
• Goal 1. Fidelity. The loader must reproduce the final LSM-
tree state that incremental construction produces to preserve
subsequent workload behavior.

• Goal 2. Flexibility. The loader must reproduce the corre-
sponding final LSM-tree state across the loading configura-
tions that experiments require.
To meet these goals, we propose F2Load, which simulates
incremental construction in memory and writes SSTs only
once. F2Load represents each SST as an in-memory descrip-
tor called a virtual SST (vSST). Each vSST stores SST meta-
data and compact summaries of its key distribution and key
set. Using these descriptors, F2Load performs virtual com-
paction to predict the output SSTs that real compaction would
produce and update the LSM-tree state in memory. F2Load
repeats virtual compaction until it reaches the final LSM-tree
state. It then materializes the final vSSTs as real SSTs in a sin-
gle materialization phase. This approach reproduces the final
LSM-tree state of incremental construction while avoiding
the I/O and CPU costs of repeatedly constructing intermediate
SSTs.
We implement F2Load on RocksDB and evaluate it on
synthetic datasets of up to 8 TB. Compared with incremen-
tal construction, F2Load accelerates dataset loading by up
to 47.9× and reduces total disk writes by up to 96.6%. The
resulting datasets exhibit similar access behavior, throughput,
and latency under YCSB and MixGraph workloads to those
loaded through incremental construction. We further evalu-
ate fidelity across different loading configurations and show

that F2Load reproduces the corresponding final LSM-tree
states while preserving subsequent workload behavior. Our
contributions are summarized as follows:
• We analyze the I/O and CPU costs of incremental con-
struction and identify repeated SST construction as a major
source of loading overhead. We show that most SSTs pro-
duced during loading are absent from the final LSM-tree
state, motivating dataset loading without materializing in-
termediate SSTs (Section 2).

• We demonstrate that the final LSM-tree state affects sub-
sequent workload behavior and depends on the loading
configuration. These findings establish fidelity and flexi-
bility as requirements for direct construction of the final
LSM-tree state (Section 3).

• We introduce virtual SSTs and virtual compaction to predict
and apply compaction-induced state changes in memory.
This process derives the final LSM-tree state without mate-
rializing intermediate SSTs, followed by a single material-
ization phase for the final SSTs (Section 4).

• We implement F2Load on RocksDB and evaluate its load-
ing performance, fidelity, and flexibility. Our evaluation
quantifies reductions in loading time and disk writes and
compares the final LSM-tree states and subsequent work-
load behavior with those of incremental construction across
multiple loading configurations (Section 5).

Background and Motivation

2.1
Dataset Loading in LSM-Tree Evaluation

Developers evaluate a storage system many times during its
development, not once. To check whether a change improves
performance, they set up the evaluation environment, run the
workload, analyze the results, and try different parameters.
This practice is known as performance regression testing, or
continuous benchmarking when it runs as part of the build
pipeline [12,26]. MongoDB’s Distributed Systems Infrastruc-
ture, for example, automates the whole cycle [14].
These evaluations require datasets at representative scales
and with data characteristics relevant to the target application.
Production data and traces are often difficult to obtain because
of collection costs and privacy concerns. They also reflect par-
ticular operating conditions, limiting the range of experiments
they can support. To address these limitations, developers use
synthetic datasets and workloads whose scale and characteris-
tics can be configured for each experiment. Benchmarks such
as YCSB [9], LinkBench [2], and TAOBench [8] provide this
capability.
We focus on synthetic dataset loading for LSM-tree based
KV stores. Dataset loading populates the store with the data
on which a subsequent evaluation workload operates. YCSB
separates this process into a load phase that populates the
database and a run phase that executes the evaluation work-
load [9,36]. RocksDB’s db_bench provides write-only work-

Dataset loading for LSM-tree based KV stores is also re-
quired when evaluating other storage components. These eval-
uations use KV stores as storage backends or application-level
benchmarks, so they must populate the stores before executing
their workloads. Examples include evaluations of distributed
databases, file systems, and storage devices using RocksDB
or LevelDB [4,13,17,25].
LSM-tree based KV stores load a dataset through repeated
flushes and compactions, a process we call incremental con-
struction. Figure 1 illustrates this process. Incoming KV pairs
are first inserted into an in-memory buffer called a memtable.
When the memtable fills, it becomes immutable and is flushed
to disk as a Sorted String Table (SST) in L0. In leveled com-
paction, SSTs selected from Li are merged with overlapping
SSTs in Li+1, and the output SSTs are written to Li+1. The
merge discards obsolete versions of keys when they are no
longer needed. Repeated flushes and compactions progres-
sively populate the LSM-tree’s levels as loading proceeds.

2.2
The Cost of Loading at Scale

LSM-Tree based KV stores are widely adopted as a stor-
age backend for write-heavy workloads and large-scale KV
data [5,7,16,27], and the data they hold keeps growing [28].
RocksDB is a representative example, and Facebook reports
that it stores hundreds of petabytes of production data across
more than 30 applications [11].
Realistic evaluation therefore requires terabyte-scale
datasets, but building one is slow. In our experiments on
RocksDB, an 8 TB dataset of 1 KB KV pairs takes 13.3 hours
to build, and a 16 TB or 32 TB dataset would take roughly
30 or 64 hours (Figure 2a). Moreover, this cost is paid again
every time the system is measured, so loading becomes the
bottleneck of the whole evaluation.
The long loading time stems from write amplification, a
problem inherent to LSM-Trees. As Figure 1 shows, an LSM-
Tree buffers incoming KV pairs in a memtable and, once that
memtable is full, marks it immutable and flushes it to disk as
a Sorted String Table (SST). In the background, compaction
merges SSTs to remove duplicate keys, reclaim space, and
reduce point-lookup cost. To do so, it reads the overlapping

SSTs of Li and Li+1 and writes their merged output back
to Li+1. As loading proceeds, repeated compactions move
data from L0 down to the deeper levels, and the amplification
arises from rewriting the same KV pair at each one. We call
this loading process incremental construction, since flush and
compaction build the final state step by step.
As the data volume grows, so does the cost of incremental
construction. A larger dataset forms more levels, so each KV
pair is rewritten more times. Compaction writes 12.2 times
the ingested data at 500 GB and 20.4 times at 8 TB. Loading
time therefore rises faster than the dataset itself, by about
2.2× each time the DB size doubles (Figure 2a). That cost is
not only disk traffic. Every rewrite must also merge the input
keys and rebuild the table, including its filters and indexes, so
each pass consumes CPU as well as I/O. Figure 2c separates
these components, and the merge and SST build time is larger
than the I/O time in every configuration.
Beyond scale, the evaluation configuration itself can in-
crease loading time. Compression is one example. KV stores
commonly enable it to reduce disk usage and I/O [1,31]. Be-
cause it makes each SST smaller, it reduces the number of
compactions. This lowers the cumulative build, merge, and
I/O time (Figure 2c). However, each compaction must now de-
compress and recompress its inputs. This added CPU cost out-
weighs the savings, so the overall loading time still increases
(Figure 2b). The KV size has a similar effect. Facebook re-
ports that the average key and value sizes in its production
RocksDB workload are 47.9 B and 42.9 B, totaling 91 B per
pair [6]. As the uncompressed bars in Figure 2b show, at
the same dataset size the 91 B configuration takes about 3×
longer to load than a 1 KB one. At 8 TB, this means 46.2
hours rather than 13.3. The reason is that smaller pairs mean
more records, which raises the cost of building filters and
indexes during SST construction and increases the number of
keys each merge must process.

2.3
Opportunity in Dataset Loading

The write amplification that makes loading slow is not spent
on the data that a benchmark will later use. Compaction
spends it rewriting SSTs that a subsequent compaction soon
replaces. In a 1 TB load, only 6.53% of the SSTs ever writ-
ten survive into the final LSM-Tree state. The rest are built,
merged, and deleted during loading.
This cost can be skipped because dataset loading is a special
case, not normal service. A KV store in service must answer
reads and scans at all times, so every state it passes through
is observable and must be correct and queryable. Dataset
loading has no such requirement. It is a preparation phase that
runs before measurement begins, and no query is ever issued
against the states it passes through.
A loader may therefore jump directly to the final state. If it
materializes only the SSTs that the final state holds, each KV
pair reaches the disk once rather than once for every level it

Design Goals for Direct Final-State Con-
struction

Directly building the final LSM-tree state without producing
the intermediate SSTs is promising but not straightforward.
The difficulty is that the final state is more than a set of SSTs,
and that the placement of those SSTs determines the lookup
and compaction behavior of a subsequent workload.
A direct final-state construction is therefore useful only
if it is fast and also meets two further requirements, fidelity
and flexibility, which the rest of this section makes precise.

접적으로는 query가 수행하는 논리적 동작에 나타난다. 곧
lookup이 확인하는 filter의 수, 그중 key를 찾는 비율, 그리
고 쓰기가 유발하는 compaction 양이다. 따라서 direct final-
state construction은 빠른 구축만으로 충분하지 않고, 동일
한 설정에서 baseline이 만들어내는 final state를 재현해야
한다.

Goal 1: Fidelity.
같은 설정에서 incremental construction
이 형성하는 final LSM-tree state를 재현해야 한다. State가
다르면 lookup이 확인하는 filter의 수, 그중 key를 찾는 비율,
쓰기가 유발하는 compaction 양이 함께 달라지기 때문이다.

3.2
Configuration Dependence of the Final
State

Direct final-state construction을 더욱 어렵게 만드는 것은,
final state가 로딩 설정에 따라 달라진다는 점이다. Key
uniqueness, compression 사용 여부, level structure의 정의,
SST size가 달라지면 만들어지는 LSM-tree의 크기와 SST
수, 그리고 SST 사이의 겹침이 함께 달라진다. 앞 절에서
보인 대로 이러한 차이는 후속 워크로드의 behavior로 이어
진다.

Key uniqueness는 중복 제거 후 남는 key를 줄이고, com-

SST size는 레벨별 데이터를 그대로 둔 채 그것이 몇 개의
파일로 나뉘는지를 바꾼다.
그 결과 만들어진 final state는 설정마다 다르다. DB 크기
는 0.27 TB에서 0.75 TB까지, SST 수는 3,237개에서 13,539
개까지 걸친다. 데이터의 총량이나 레벨 용량을 바꾼 설정
은 쓰는 레벨이 달라져서, key uniqueness를 낮춘 state는 L4
에서 끝나고 level structure를 바꾼 state는 L6까지 내려간다.
반면 SST size를 바꾼 state는 레벨별 데이터가 baseline과 같

끝나므로, 이 차이는 오류가 아니라 그 설정이 만드는 state
그 자체다.
Final state의 차이는 workload behavior의 차이로 드러난
다. Lookup은 위 레벨부터 후보 SST의 filter를 확인하다가
key를 찾으면 멈추므로, 데이터가 아래 레벨에 몰려 있을수
록 확인하는 filter가 늘어난다. Level structure를 바꾼 state
는 레벨 하나의 용량이 작아져 데이터의 99%가 가장 아래
레벨에 놓이고, 그만큼 확인하는 filter가 baseline보다 늘어
난다. Compression을 켠 state는 레벨 수가 baseline과 같지
만, 레벨의 용량이 압축 후 크기로 정해져 위 레벨들이 담는
양은 그대로인 채 가장 아래 레벨만 489 GB에서 113 GB
로 줄어든다. 아래 레벨에 놓인 데이터의 비중이 65%에서
30%로 낮아지므로 lookup이 더 위에서 key를 찾고, 확인하
는 filter는 줄어든다. Key uniqueness를 낮춘 state는 쓰는
레벨 자체가 하나 줄어 마찬가지로 줄어든다. SST size를
바꾼 state는 레벨 구성이 baseline과 같은데도 SST 하나가
담는 key range가 넓어져 확인하는 filter가 늘어난다. 확인
하는 filter가 적은 state일수록 throughput이 높다.
지금까지의 결과는 final state가 로딩 설정에 종속적임을
보인다. 따라서 direct final-state construction은 하나의 설정
에서 성립하는 것으로 충분하지 않다. 설정이 바뀌면 재현
해야 할 대상 자체가 달라지므로, 설정을 입력으로 받아 그
설정이 만드는 state를 따라갈 수 있어야 한다.

Goal 2: Flexibility.
로딩 설정이 달라져도 그 설정의 in-
cremental construction이 형성하는 final state를 재현해야

3.3
Reusing or Predicting the Final State

한 번 만든 state를 snapshot이나 백업으로 저장해 두고 재
사용하는 방식은 두 goal을 함께 만족하지 못한다. 저장된
state는 그것을 만든 설정에서만 incremental construction
의 결과와 일치하므로, 설정이 하나라도 바뀌면 재현해야
할 대상이 달라져 fidelity를 잃는다. 게다가 앞 절의 축들
은 서로 독립적으로 조합된다. 네 축에 각각 값을 서너 개
씩만 두어도 조합은 수백 개가 되고, DB size와 KV size,
compaction policy까지 축으로 더하면 그 수는 곱으로 늘
어난다. 이 조합들을 미리 갖추려면 각각에 대해 baseline
로딩을 되풀이해야 하므로, 로딩 비용을 없애는 것이 아니
라 앞당겨 치르는 것에 가깝다.
설정으로부터 final state를 계산하거나 예측하는 방식도
성립하기 어렵다. 로딩 설정의 변화는 compaction이 언제
실행되는지, 어떤 SST를 입력으로 고르는지, 그 입력이 어
떤 데이터인지, 결과 SST를 어떤 조건으로 끊는지를 바꾼
다. 이러한 결정은 compaction job 하나의 동작 단위에서
이루어지며, 그 동작이 반복해서 쌓인 결과가 final state다.
따라서 state의 변화를 따라가지 않고 미리 정의된 수식이나
규칙만으로 final state를 얻기는 어렵다. 결국 incremental
construction이 수행하는 compaction을 제거하더라도, final
state를 구하려면 그 compaction이 LSM-tree state를 어떻게
바꾸는지 추적해야 한다.

4
F2Load Design

In this section, we present our methodology for fast-
forwarding dataset loading while achieving fidelity and flex-
ibility. The core principle of F2Load is to follow the in-
cremental construction process while simulating flush and
compaction using a small SST descriptor called virtual SST
(vSST). All simulation takes place in memory, and F2Load
finally materializes the surviving vSSTs into actual SSTs on
disk to construct the final state of the LSM-tree. Figure 7
shows F2Load’s loading pipeline.

4.1
Virtual SST Registration

A vSST is a small in-memory structure that retains only the
information required for virtual compaction and materializa-
tion. It consists of three components as illustrated in Table 1:
(1) SST metadata to follow the compaction policy, (2) a set of
index models to approximate the key distribution of the SST,
and (3) a KMV sketch to deduplicate keys during merging. We
describe each component in detail as follows.

SST Metadata.
SST metadata retains the information re-
quired to simulate compaction during incremental construc-
tion. It includes the information needed to reproduce com-
paction triggering and input file selection, generate output
vSSTs, and materialize actual SSTs afterward.
In LSM-trees, compaction triggering depends on whether a
level’s total size or file count exceeds a threshold, while input
file selection depends on the key ranges of SSTs. Neither
requires individual KV pairs in an SST. Accordingly, each
vSST stores four fields in SST metadata: file size, key range,
SST ID, and KV pair count.
File size is used to maintain the total size of each level.
Whenever a vSST is added to or removed from a level, F2Load
updates the corresponding aggregate statistics. Key range is
used for input file selection: F2Load checks whether vSST
ranges overlap to expand the inputs of a virtual compaction
across adjacent levels. Once the input vSSTs are selected, their
SST IDs identify the corresponding vSST objects to merge.
The KV pair count is not required for compaction triggering
or input file selection. Instead, F2Load uses it to approximate
the result of a virtual compaction, which generates the output
vSSTs, and to materialize actual SSTs afterward.
A vSST does not store its level or per-level statistics. In-
stead, LSM-KVS maintains a separate structure (e.g., version
set) that tracks the SSTs in each level, their aggregate statistics,

0,1,...,No −1을 순회하며, PLR의 inverse k = r−1
o (p)로 key
를 생성해 real SST에 기록을 시도한다. 같은 non-L0 level
의 인접 vSST가 boundary key를 공유하면 뒤 range의 lower
bound를 앞 range의 maximum보다 1 큰 key로 조정한다.
Rounding으로 동일하거나 감소하는 key가 생성되면 이전
key보다 크게 보정하며, 이 보정값이 vSST의 upper bound
를 넘으면 해당 range의 생성을 종료한다. 따라서 approxi-
mation과 boundary correction 때문에 실제로 기록되는 수는
No보다 작을 수 있다. Deduplication correction은 split 전에
이미 rank count와 distribution에 반영되었으므로, material-
ization에서 KMV를 다시 적용하거나 final vSST 사이의 key
list를 merge하지 않는다. 각 vSST는 독립적으로 material-
ize할 수 있어 여러 worker가 병렬로 SST를 생성한다. 이후
benchmark workload는 이 real SST들에 RocksDB의 일반
read/write path로 접근한다.
KMV와 PLR은 original key identity 전체를 보관하지 않
으므로, 이 과정은 original union을 exact하게 복원하는 것
이 아니라 corrected rank마다 하나의 approximate key를 생
성한다. 따라서 KMV가 보존하는 것은 deduplicated cardi-
nality와 range별 density이며, current prototype의 live-key
membership 한계는 Figure ??에서 별도로 확인한다.

4.4
Implementation

F2Load은 Facebook이 개발한 level-based LSM-tree인
RocksDB에 구현하였다. Registered vSST는 RocksDB의 일
반 compaction picker에 보이며, picker가 선택한 input과
output level을 그대로 사용해 background thread에서 vir-
tual compaction을 실행한다. 구현은 Step 1의 PLR merge
와 Step 2의 range-local KMV correction을 한 번의 model-
construction pass로 fuse한 뒤, corrected model을 Step 3의
split routine에 전달한다. Data I/O를 제거한 뒤에는 LSM-
tree metadata update가 새로운 병목이 되므로, 여러 Ver-
sionEdit을 batch로 처리하고 write-only loading 중 사용하
지 않는 metadata work를 미룬다. Materialization이 끝나면
virtual file을 real SST metadata로 교체하여 일반 RocksDB
state로 전환한다.

5.2
Comparison against Write-path Optimiza-
tions

기존 연구들은 incremental construction의 write path를 유
지하면서 background work의 실행 방식이나 compaction 과
정에서 이동하는 데이터양을 줄이는 방식으로 write path를
최적화해 왔다. 대표적으로 ADOC은 thread 수와 memtable
size를 동적으로 조정하여 flush와 compaction 간의 데이터
흐름을 최적화한다 [37]. 반면 BlobDB는 key와 value를 분
리하고 value를 별도의 file에 저장함으로써, compaction 과
정에서 발생하는 value 재작성을 줄인다 [19,32]. Figure ??
는 24 B key와 1,000 B value로 구성된 1 TB 데이터셋을 대
상으로 Baseline과 두 write-path optimization 기법을 비교한
결과를 보여준다.

Dataflow tuning.
ADOC은 compaction work를 제거하지
않고 그 input buffer size(memtable,SST)와 compaction을
수행하는 background thread 수를 조절한다. 그러나 본 실
행에서 ADOC의 loading time은 68.7분으로, Baseline보다
17.7% 길었다. ADOC은 buffer size를 키움으로써 device-
level WAF를 13.50에서 11.16으로 낮추고 compaction 수를
60.1% 줄였지만, compaction당 평균 read size는 257.1 MiB
에서 530.5 MiB로, 평균 duration은 0.692초에서 1.328초로
각각 2.06×와 1.92× 증가하였다. Compaction 횟수는 줄
었지만 각 job은 더 크고 오래 실행되었다. Compaction의
입력 단위가 커지면 한 번에 L1과 L2로 밀려 내려가는 부
하도 그만큼 커진다. RocksDB는 아직 compaction되지 않은
데이터양이 임계값을 넘으면 foreground write를 지연시키
거나 정지시키므로, 부하가 이렇게 한꺼번에 쌓이면 임계
값을 넘는 일이 더 잦아진다. 그 결과 ADOC의 write stall
time은 2,347초에서 3,002초로 27.9% 증가하였고, 이는 감
소한 compaction 비용을 상쇄한다.

Key–value separation.
BlobDB는 key와 value를 분리하
여 compaction의 오버헤드를 감소시키기 위한 구조이다.
Value를 별도의 파일에 저장하고, SST에는 key와 value의
reference만 저장한다. Compaction은 실제 value 대신 key와
value reference만 처리하므로, 더욱 적은 CPU 비용과 I/O 비
용으로 처리될 수 있다. 그 결과 loading time은 28.5분으로
Baseline보다 2.05× 빨라졌다. 이 실행에서는 최대 가속화
정도를 측정하기 위해 value가 저장된 파일을 주기적으로
정리하는 garbage collection (GC)을 비활성화하였다. 실험
이 24 B라는 작은 key size를 대상으로 하였기에 로딩 가속
화를 더욱 극대화할 수 있었다.

5.3
Virtual Compaction Accuracy

Reproducing the final state correctly depends on how accu-
rately virtual compaction predicts each compaction’s output.
A wrong prediction produces a wrong DB state. To evaluate
this, we ran a baseline RocksDB load. For every compaction,
we built vSSTs from its input SSTs and ran virtual compaction
on them in parallel. We collected 21,828 compaction jobs and
evaluated the accuracy of its two tasks, merge and split, and
deduplication.

Merge and split
Virtual compaction predicts the exact out-
put SST count for 90.9% of jobs and stays within ±1 file for
99.8%, with a maximum error of ±3 (Figure 10a). This holds
across all level transitions, regardless of compaction depth.
The output size is just as close (Figure 10b), with a median
error of 1.15%.

Deduplication
Deduplication relies on the KMV sketch’s
cardinality estimate, which has a mean absolute error of 1.62%
and a median of 1.16% (max 11.7%). This keeps both the
deduplication correction and the size prediction accurate.
Overall, virtual compaction reproduces the count and size
of compaction output to within a few percent using only de-
scriptors.

5.4
Final State Fidelity

F2Load’s goal is to reproduce the state that incremental con-
struction would build. F2Load predicts compaction outputs
rather than performing them. We must therefore check that
the reproduced state is close to the baseline. We verify this
in two ways. The first is a large-scale case study on a single
10 TB dataset of 1 KB KV pairs. The second is a sweep across
various configurations. We compare the two states by ana-
lyzing how the same benchmark behaves on them and their
structural properties such as final DB size, SST count, and
average SST size.

Large-scale case study
We build a single 10 TB dataset of
1 KB KV pairs with no compression. On both the baseline
state and the F2Load-built state, we run seven workloads
(YCSB A–F [9] and MixGraph [6]) and compare throughput,
tail latency, disk read, and disk write (Figure 11).
Disk read is the I/O that point lookups issue, and F2Load
tracks the baseline on every workload. Disk write comes
from compaction, so it appears only in workloads that write.
The read-only workload C therefore produces almost no write,
while the write-heavy workloads A and F trigger the most. Tail
latency also tracks the baseline closely. These results indicate
that the state built by F2Load preserves the baseline’s read
and compaction behavior across the evaluated workloads.

Configuration sweep
To confirm that this fidelity is not spe-
cific to one setting, we sweep 12 configurations that combine
two KV sizes (1 KB, 91 B), two DB sizes (500 GB, 1 TB), and
three key patterns (uniform and zipfian at 50% unique keys,

and unique at 100% unique keys). For each configuration,
Figure 12 reports F2Load’s value normalized to the baseline
for seven metrics in two groups. Three capture the loaded
state (DB size, SST count, and SST size), and four capture
how a read-only workload (YCSB C, zipfian 0.99) behaves
on it (throughput, average latency, disk read, and SST access).
An SST access adds no disk I/O while RocksDB pins each
SST’s filter and index in memory, but it would bound read
throughput under memory pressure. Across the configurations
F2Load stays close to the baseline on every metric.

Comparison against the design alternatives
We place
F2Load on the same 1 TB dataset used for the design alter-
natives of Section 3 (1,000 GiB of 24 B keys and 1,000 B
values) so that its state can be read against theirs. Loading
takes 134.7 seconds in total: a 97.0-second run that includes
materialization, which leaves 16.07 GiB of estimated pend-
ing compaction, followed by 37.8 seconds during which a
checkpoint reopened under the common clean release drains
that backlog to zero pending bytes. The completion stage
reads 21.64 GiB and writes 19.55 GiB of real SSTs, and the
reported time is the sum of the two process wall times, so it
includes that additional physical compaction. All reads below
run on this completed DB under the reader of Figure ??.
On filter checks per lookup, F2Load sits where the baseline
sits and where no alternative does. It checks 3.53 filters per
request with 18.29% of those checks positive, against the
baseline’s 3.98 and 16.69%; Flush-only inflates the same
metric to 10254.44 checks, while one-shot compaction and
Fillseq collapse it to 1.00. Read throughput is 1.04–1.70× the
baseline across the four cache configurations.
Live-key membership is where the current prototype falls
short. The metadata-only path does not carry original key
identity, so it reconstructs the key set approximately from a
KMV sketch and a learned-index descriptor. The resulting
successful-lookup fraction is 61.81% against the baseline’s
63.21%, a gap of 1.40 percentage points. F2Load therefore
reproduces candidate-SST composition, which no alternative
does, but not exact key membership; the throughput above
should be read as evidence in that context rather than as a
controlled layout-only speedup. Each cell is a single run, and
F2Load was measured after the five alternative states rather
than interleaved with them.

6
Conclusion

Loading a dataset is the first step of every LSM-Tree eval-
uation, and at terabyte scale it becomes a bottleneck on its
own, because compaction rewrites the same data many times.
We presented F2Load, which reproduces this final state with-
out paying that cost. Its key idea is that the outcome of
compaction can be predicted from a compact summary of
each SST. F2Load therefore replaces each SST with an in-
memory virtual SST, runs virtual compaction along the orig-
inal compaction path, and materializes real SSTs only once
the final state is fixed. It avoids intermediate materialization;
the measured prototype also performs physical completion
compactions after materialization. In the common 1,000 GiB,
1 KB comparison, F2Load reduces loading time by 25.99×
and device writes by 94.1%, including physical completion
compactions. The separate historical scaling series builds an
8 TB dataset of 91 B pairs in under two hours, a load the
baseline would need a projected 47 hours to finish. Sepa-
rate historical experiments compare the reproduced state and
workload behavior across configurations. The new common
comparison also exposes a key-membership difference, so its
read-throughput ratios do not isolate layout effects.
